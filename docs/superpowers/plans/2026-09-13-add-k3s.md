# Add k3s Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Install `k3s-bin` (+ `kubectl`, `helm`, `k9s`) and run a persistent single-node cluster: server config deployed, `k3s.service` enabled, user shell pointed at the world-readable kubeconfig.

**Architecture:** `k3s-bin` goes into `_aur.yml` (no official-repo k3s exists; the AUR source build takes hours), companions into `_pacman.yml`. A new `k3s` app deploys `/etc/rancher/k3s/config.yaml` (`write-kubeconfig-mode: "644"`) — software role runs before services, so the mode applies to the first generated kubeconfig. A central zsh fragment exports `KUBECONFIG`. `k3s` joins `system_units` in `group_vars/all.yml`.

**Tech Stack:** Ansible (`community.general.pacman`, `ansible.builtin.copy`, `ansible.builtin.systemd` via services role), AUR `k3s-bin` (ships `k3s.service`, `ExecStart=/usr/bin/k3s server`, default config path `/etc/rancher/k3s/config.yaml`).

## Global Constraints

- Follow the `include_tasks` + module-arg `apply: tags:` + outer `tags:` pattern for the new app include (plain `tags:` on a dynamic include does not reach inner tasks).
- All numbered zsh fragments live in `roles/software/files/zsh/` and deploy via the existing `with_fileglob: "zsh/[0-9]*.zsh"` — do NOT deploy fragments from the k3s app.
- Do NOT touch `/etc/systemd/system/k3s.service.env` (package-owned).
- Do NOT modify `~/.zshrc` (user-owned).
- README.md and README.zh.md must stay in sync; AGENTS.md counts must match reality.
- Commit messages in English per repo convention (`packages: …`, `<app>: …`).
- Static checks: `cd playbooks && ansible-playbook site.yml --syntax-check && ansible-lint`.

### Task 2: k3s app — server config, include, service enable

**Files:**
- Create: `playbooks/roles/software/files/k3s/config.yaml`
- Create: `playbooks/roles/software/tasks/k3s.yml`
- Modify: `playbooks/roles/software/tasks/main.yml` (new include between the kimi and kitty blocks)
- Modify: `playbooks/inventory/group_vars/all.yml` (append to `system_units`)

**Interfaces:**
- Consumes: `k3s.service` unit file from Task 1's `k3s-bin` package.
- Produces: `/etc/rancher/k3s/config.yaml` (root:root 0644) deployed before services start k3s; `k3s` app tag; `k3s` in `system_units` (services role enables+starts it). Task 3 relies on the kubeconfig path `/etc/rancher/k3s/k3s.yaml` being world-readable, which this task's config guarantees from first start.

- [ ] **Step 1: Create the server config**

Create `playbooks/roles/software/files/k3s/config.yaml`:

```yaml
write-kubeconfig-mode: "644"
```

- [ ] **Step 2: Create the app task**

Create `playbooks/roles/software/tasks/k3s.yml`:

```yaml
---
# Root-owned server config; software runs before services, so this is in
# place before k3s.service first starts — the generated kubeconfig is 644
# from the start (user kubectl access without file copies).
- name: Deploy k3s server config
  become: true
  ansible.builtin.copy:
    src: k3s/config.yaml
    dest: /etc/rancher/k3s/config.yaml
    owner: root
    group: root
    mode: "0644"
```

- [ ] **Step 3: Wire the include into main.yml**

In `playbooks/roles/software/tasks/main.yml`, between the `- name: "App: kimi"` block and the `- name: "App: kitty"` block, insert:

```yaml
- name: "App: k3s"
  ansible.builtin.include_tasks:
    file: k3s.yml
    apply:
      tags: k3s
  tags: k3s
```

- [ ] **Step 4: Enable the service**

In `playbooks/inventory/group_vars/all.yml`, append to `system_units` (after `- sddm`):

```yaml
  - k3s
```

- [ ] **Step 5: Verify static checks + dry run**

```bash
cd playbooks && ansible-playbook site.yml --syntax-check && ansible-lint
ansible-playbook site.yml --check --tags k3s
```

Expected: static checks pass; dry run shows the copy task (changed or ok, no failures).
